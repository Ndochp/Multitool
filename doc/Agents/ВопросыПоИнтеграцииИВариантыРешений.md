# Вопросы по интеграции с внешними Issue трекерами и варианты решений

## Вопрос 1: Конфликт внешних идентификаторов при синхронизации

**Проблема:** Что делать, если один и тот же внешний идентификатор тикета (например, IID в GitLab) уже существует в справочнике Тикеты, но ссылается на другой элемент 1С? Возможна ли ситуация, когда тикет был привязан к одному проекту, а затем перенесён в другой?

**Варианты решения:**
- **Вариант А (строгая уникальность):** ВнешнийИдентификатор + ВнешняяСистема — уникальный реквизит на уровне справочника. При синхронизации тикет обновляется, но не дублируется. Перенос между проектами отражается в регистре МаппингТикетовПроектов1С.
- **Вариант Б (версионирование):** Создаётся новая запись тикета при каждом изменении привязки к проекту. Старая помечается как `ПометкаУдаления = Истина`.

**Рекомендация:** Вариант А — проще, меньше данных, достаточно для большинства сценариев.

## Вопрос 2: Стратегия синхронизации таймлогов при удалении тикета во внешней системе

**Проблема:** Что происходит с записями ТаймшитыВнешнихСистем, если тикет был удалён или архивирован во внешней системе?

**Варианты решения:**
- **Вариант А (мягкое удаление):** При синхронизации помечать тикет `ПометкаУдаления = Истина`, записи таймшитов сохранять.
- **Вариант Б (жесткое удаление):** Удалять все связанные записи таймшитов при удалении тикета.

**Рекомендация:** Вариант А — данные таймшитов важны для расчёта заработной платы, их потеря может привести к финансовым расхождениям.

## Вопрос 3: Множественные внешние системы и конфликты токенов

**Проблема:** Если в конфигурации настроено несколько внешних систем (GitLab + Jira), как хранить и управлять токенами? Хранить ли токены в `ВнешниеСистемыТикетов` или вынести в отдельный регистр сведений с шифрованием?

**Варианты решения:**
- **Вариант А (токен в карточке системы):** Простое решение, токен хранится в реквизите `ТокенДоступа`. Недостаток: токен виден всем, кто открывает карточку системы.
- **Вариант Б (отдельный регистр сведений "ТокеныИнтеграций"):** Токены хранятся в отдельном защищённом регистре с измерением `ВнешняяСистема`. Позволяет ротацию токенов без изменения карточки системы.

**Рекомендация:** Вариант Б — более гибкий, позволяет хранить несколько версий токенов (текущий/старый) и обеспечивает безопасность.

## Вопрос 4: Пагинация при выгрузке больших объёмов данных

**Проблема:** GitLab API возвращает максимум 100 записей за запрос. При синхронизации сотен тикетов/таймлогов требуется обработка пагинации. Как реализовать?

**Варианты решения:**
- **Вариант А (полная синхронизация):** Проходить по всем страницам, накапливать все записи. Долго, но надёжно.
- **Вариант Б (инкрементальная синхронизация):** Синхронизировать только изменения с `ДатаПоследнейСинхронизации`. Использовать параметры `updated_after` API GitLab.

**Рекомендация:** Вариант Б — значительно быстрее, меньше нагрузка на внешнюю систему. Требует хранения `ДатаПоследнейСинхронизации` для каждой внешней системы.

## Вопрос 5: Маппинг сотрудников — автоматический vs ручной

**Проблема:** Как определять связь между сотрудником 1С и пользователем во внешней системе?

**Варианты решения:**
- **Вариант А (ручной маппинг):** Администратор вручную связывает каждого сотрудника с пользователем внешней системы через справочник `ПользователиВнешнихСистем.Сотрудник1С`.
- **Вариант Б (автомаппинг по email/логину):** При синхронизации пользователей система автоматически ищет сотрудника с совпадающим email или логином. При нахождении — создаёт связь автоматически.

**Рекомендация:** Вариант Б + Вариант А: автомаппинг работает для большинства сотрудников, нераспознанные пользователи помечаются как `ТребуетсяМаппинг` и отображаются в отдельном списке для ручного назначения.

## Вопрос 6: Обработка ошибок API — политика повторных попыток

**Проблема:** Как обрабатывать временные ошибки (503, таймауты) при синхронизации?

**Варианты решения:**
- **Вариант А (экспоненциальная задержка):** 1-я попытка → ждать 2 сек, 2-я → 4 сек, 3-я → 8 сек. Максимум 5 попыток.
- **Вариант Б (фиксированная задержка):** 3 попытки с интервалом 5 секунд.

**Рекомендация:** Вариант А — более щадящий для внешней системы, снижает риск получения 429 (Too Many Requests).

## Вопрос 7: Фоновая синхронизация vs онлайн

**Проблема:** Синхронизация больших объёмов данных может занимать длительное время. Запускать ли её в фоновом задании или позволять пользователю ждать результат?

**Варианты решения:**
- **Вариант А (только фоновое задание):** Пользователь запускает синхронизацию → создаётся фоновое задание → результат отображается в журнале заданий. Плюс: не блокирует интерфейс. Минус: задержка результата.
- **Вариант Б (гибридный):** Малые объёмы (< 100 записей) — онлайн, большие — автоматически в фоне.

**Рекомендация:** Вариант А — проще в реализации, предсказуемое поведение. Результат синхронизации отображается в журнале заданий с возможностью просмотра прогресса.

## Вопрос 8: Структура возврата данных из обработки интеграции

**Проблема:** В текущей реализации методы `ПолучитьTimelogи` и `ПолучитьTimelogиПоСотруднику` возвращают ТаблицуЗначений с техническими колонками (`timelog_id`, `issue_iid`). Нужно ли добавить методы с бизнес-интерфейсом, которые возвращают данные через ссылки на справочники 1С?

**Варианты решения:**
- **Вариант А (два уровня методов):** Сохранить текущие методы для технических задач + добавить новые `ПолучитьТаймлогиПоСотрудникуБизнес(Сотрудник, ДатаНач, ДатаКон)`, которые внутри маппят данные.
- **Вариант Б (унификация):** Заменить текущие методы на бизнес-версии, а технические поля (`timelog_id`) оставить как ресурс в ТаблицеЗначений для обновления/удаления.

**Рекомендация:** Вариант А — обратная совместимость + новый чистый интерфейс. Методы с бизнес-интерфейсом получают префикс `Бизнес` или суффикс `_Бизнес`.

## Вопрос 9: Хранение тела/описания тикета

**Проблема:** Описание тикета в GitLab может быть большим (Markdown, HTML). Хранить ли полный текст в реквизите `Описание` справочника Тикеты или вынести в отдельный регистр сведений/документ?

**Варианты решения:**
- **Вариант А (в карточке тикета):** Реквизит `Описание` типа Строка, 5000 символов. Просто, но ограничено по объёму.
- **Вариант Б (отдельный документ "ИсторияТикета"):** Каждый комментарий/изменение тикета — отдельная запись документа. Полный текст хранится в документе.

**Рекомендация:** Вариант А для основного описания + Вариант Б для комментариев: история изменений тикета (комментарии) хранится в регистре сведений `КомментарииТикетов`.

## Вопрос 10: КоннекторHTTP — поддержка методов Post, Put, Delete

**Проблема:** В текущей реализации `КоннекторHTTP` (из теста) определён только метод `Get`. Нужно ли расширить модуль `КоннекторHTTP` методами `Post`, `Put`, `Delete` или создать отдельный модуль `КоннекторHTTPFull`?

**Варианты решения:**
- **Вариант А (расширение текущего модуля):** Добавить методы Post, Put, Delete в существующий общий модуль `КоннекторHTTP`.
- **Вариант Б (отдельный модуль):** Создать `КоннекторHTTPFull` с полным набором методов, а текущий оставить как заглушку для тестов.

**Рекомендация:** Вариант А — один универсальный модуль `КоннекторHTTP` со всеми методами. Это соответствует принципу единого транспортного адаптера.
