# Архитектура подсистемы Интеграция с GitLab (GitLab.mirror)

## 1. Общая концепция

Изолированная библиотека для работы с GitLab API из конфигурации 1С. Обеспечивает синхронизацию времени из «ЛистаУчетаРабочегоВремени» в GitLab через Timelogs API, а также прямой просмотр и управление таймлогами.

**Принцип изоляции:** весь код работы с HTTP и GitLab API сосредоточен в этой подсистеме. Документ «ЛистУчетаРабочегоВремени» не содержит HTTP-вызовов, а взаимодействует только через ФасадВнешнихСистем.

## 2. Структура подсистемы

### 2.1 Общие модули

#### Модуль «HTTPКоннектор» (готовый)
Библиотека для выполнения HTTP-запросов из 1С. Предоставляет методы:
- `ВыполнитьGET(URL, Заголовки)` — GET запрос
- `ВыполнитьPOST(URL, ТелоЗапроса, Заголовки)` — POST запрос
- `ВыполнитьDELETE(URL, Заголовки)` — DELETE запрос
- `ВыполнитьPUT(URL, ТелоЗапроса, Заголовки)` — PUT запрос

#### Модуль «GitLabAPI»
Модуль для работы с GitLab API. Использует HTTPКоннектор.

**Методы:**

1. **Инициализация**
   - `УстановитьБазовыйURL(БазовыйURL)` — установка базового URL GitLab сервера
   - `УстановитьТокен(Токен)` — установка токена аутентификации

2. **Работа с задачами (Issues)**
   - `ПолучитьНазначенныеЗадачи(ИдентификаторПользователя, Состояние)` — GET /api/v4/issues?assignee_id=...&state=opened
   - Возвращает ТаблицуЗначений: ID, IID, Title, WebURL, ProjectID

3. **Работа с таймлогами (Timelogs)**
   - `ДобавитьЗатраченноеВремя(ПроектID, IssueIID, ДлительностьВСекундах, ДатаРаботы, Описание)` — POST /projects/:id/issues/:issue_iid/time_spent
   - `УдалитьTimelog(ПроектID, IssueIID, TimelogID)` — DELETE /projects/:id/issues/:issue_iid/timelogs/:timelog_id
   - `ПолучитьTimelogи(ПроектID, IssueIID, ДатаНач, ДатаКон)` — GET /projects/:id/issues/:issue_iid/timelogs?spent_at_on_or_after=...&spent_at_before=...
   - `ПолучитьСтатистикуВремени(ПроектID, IssueIID)` — GET /projects/:id/issues/:issue_iid/time_stats

4. **Работа с проектами**
   - `ПолучитьПроекты(Состояние)` — GET /api/v4/projects?membership=true&state=active
   - Возвращает ТаблицуЗначений: ID, Name, WebURL, NamespacePath

#### Модуль «ФасадВнешнихСистем»
Единая точка входа для бизнес-логики таймтрекинга. Делегирует вызовы конкретным API-модулям в зависимости от типа системы.

**Методы:**

1. **ПолучитьСписокЗадач(ТипСистемы, ИдентификаторПользователя)**
   - Возвращает ТаблицуЗначений для заполнения выпадающего списка на форме
   - Внутри по типу системы вызывает соответствующий API

2. **ДобавитьЗатраченноеВремя(Задача, ДлительностьВСекундах, ДатаРаботы, Описание)**
   - По ТипуВнешнейСистемы и ВнешнемуИдентификатору вызывает нужный API-метод
   - Возвращает ID созданной записи (TimelogID)

3. **УдалитьЗатраченноеВремя(Задача, IDTimelog)**
   - Удаляет существующую запись времени

4. **ПолучитьТаймлогиЗаПериод(ВнешняяСистема, ДатаНач, ДатаКон, Задача)**
   - Возвращает ТаблицуЗначений с таймлогами за указанный период
   - Используется формой «ТаймлогиGitLab»

5. **УдалитьЗатраченноеВремяПоДате(Задача, Дата)**
   - Удаляет все timelog'и для задачи на указанную дату
   - Используется для идемпотентной синхронизации

### 2.2 Форма «ТаймлогиGitLab»

Назначение: прямой просмотр и управление таймлогами в GitLab, независимо от документа «ЛистУчетаРабочегоВремени».

#### Параметры отбора
- **ВнешняяСистема** — выбор из справочника «ВнешниеСистемы»
- **Дата** — конкретная дата или период (начало/конец)
- **Задача** — опционально, фильтр по конкретной задаче
- **Пользователь** — если API позволяет

#### Таблица результатов
| Колонка | Описание |
|---------|----------|
| ID записи | timelog_id из GitLab |
| Дата/время начала | spent_at |
| Длительность | секунды (с форматированием в часы/минуты) |
| Задача | issue iid + название задачи |
| Описание | summary |

#### Действия
- **Удалить выбранную запись** — DELETE через API с подтверждением
- **Открыть веб-страницу задачи** — переход по ссылке на Issue в GitLab
- **Экспорт в Excel/MXL** — выгрузка результатов в табличный документ

## 3. Алгоритм синхронизации

### 3.1 Вызов из формы документа
Синхронизация запускается по кнопке «Синхронизировать с GitLab» на форме документа «ЛистУчетаРабочегоВремени».

### 3.2 Пошаговый алгоритм

#### Шаг 1: Подготовка данных
- Получить строки документа
- Исключить строки без интеграции (Обед, локальные)
- Подставить ЗадачуПоУмолчанию если задача не указана

#### Шаг 2: Группировка последовательных строк
- Группировка по последовательным строкам с одинаковой задачей
- Вычисление суммарной длительности и уникальных комментариев для каждой группы

#### Шаг 3: Создание/обновление timelog'ов
- Проверка существующей записи по ИдентификаторуЗаписиВремени
- Удаление старой записи через API если она существует
- Создание новой записи через GitLabAPI.ДобавитьЗатраченноеВремя()
- Запись нового ID во все строки группы

#### Шаг 4: Обновление состояния документа
- При успешной синхронизации — состояние «Синхронизирован»
- При ошибке — строки помечаются индикатором ошибки, состояние остаётся «Завершён»

### 3.3 Обработка ошибок
- **GitLab недоступен** — сообщение пользователю, идентификаторы не сбрасываются
- **Issue не найден** — сообщение с указанием задачи и IssueID
- **Токен истёк** — предложение обновить токен в настройках
- **Лимит API** — повторная попытка через заданный интервал

## 4. Управление соответствием строк и timelog'ов

### 4.1 Хранение идентификаторов
Идентификаторы timelog'ов хранятся непосредственно в табличной части документа «ЛистУчетаРабочегоВремени» в реквизите `ИдентификаторЗаписиВремени`.

### 4.2 Отслеживание актуальности
При изменении любой строки (время, задача, удаление/вставка строк):
1. Для затронутых строк `ИдентификаторЗаписиВремени` помечается как неактуальный.
2. На форме такие строки подсвечиваются жёлтым индикатором.
3. При следующей синхронизации старые timelog'и удаляются и создаются новые.

### 4.3 Групповое соответствие
При группировке строк в одну запись, одинаковый `ИдентификаторЗаписиВремени` записывается во все строки группы. Это позволяет:
- Отслеживать какие строки объединены в одну запись GitLab
- При изменении одной строки — помечать всю группу как требующую пересинхронизации

## 5. Настройки подключения

### 5.1 Справочник «ВнешниеСистемы»
Хранит общие настройки подключений (без привязки к пользователю):
- **БазовыйURL** — адрес GitLab сервера
- **ПараметрыПодключения** — тип аутентификации, заголовки

### 5.2 Регистр сведений «НастройкиПользователейВнешнихСистем» (опционально)
Для персонализированных токенов:
- **Измерения**: Пользователь1С, ВнешняяСистема
- **Ресурс**: ТокенДоступа

## 6. Расширяемость на другие системы

Архитектура позволяет легко добавлять новые внешние системы:

1. Новое значение в «ТипВнешнихСистем» (например, Jira).
2. Новый модуль API (например, `JiraAPI`) с методами работы с системой.
3. Регистрация в `ФасадВнешнихСистем` (диспетчеризация по типу системы).
4. Настройка подключения в справочнике «ВнешниеСистемы».

Работник продолжает пользоваться тем же интерфейсом без изменений.

## 8. API эндпоинты GitLab

### 8.1 Issues (Задачи)
| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| GET | `/api/v4/issues?assignee_id={id}&state=opened` | Получить назначенные задачи |
| GET | `/api/v4/projects/{id}` | Получить информацию о проекте |

### 8.2 Timelogs (Записи времени)
| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| POST | `/projects/{id}/issues/{iid}/time_spent` | Добавить затраченное время |
| DELETE | `/projects/{id}/issues/{iid}/timelogs/{timelog_id}` | Удалить запись времени |
| GET | `/projects/{id}/issues/{iid}/timelogs?spent_at_on_or_after={date}&spent_at_before={date}` | Получить таймлоги за период |
| GET | `/projects/{id}/issues/{iid}/time_stats` | Получить статистику времени |

### 8.3 Формат запроса добавления времени (POST)
```json
{
    "duration": "1h30m",
    "spent_at": "2024-01-15T10:00:00Z",
    "summary": "Описание выполненной работы"
}
```

### 8.4 Формат ответа (содержимое time_stats)
```json
{
    "time_spent": 5400,
    "total_time_spent": 14400
}
```

## 9. Безопасность

- Токен аутентификации хранится в защищённом хранилище или регистре сведений.
- HTTP-запросы выполняются по HTTPS.
- При ошибке аутентификации — токен не сбрасывается, предлагается обновить.
- Логирование успешных и неудачных вызовов API (опционально).
