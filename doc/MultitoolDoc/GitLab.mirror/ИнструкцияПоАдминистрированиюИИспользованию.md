## 1. Общие сведения

### 1.1 Назначение подсистемы

Подсистема **GitLab.mirror** обеспечивает интеграцию 1С с корпоративным GitLab  Основные функции:

- Замена хождения по гитлабу на собственный клиент
- Доступ к API и Graphql гитлаба из 1С
- Отражение задач гитлаба в 1С, чтобы можно было снабжать их собственными невидимыми в гитлабе свойствами для удобной фильтрации алертинга и тп.
- 

### 1.2 Ключевые компоненты

| Компонент                      | Описание                                          |
| ------------------------------ | ------------------------------------------------- |
| `ИнтеграцияGitLab`             | Обработка интеграции с GitLab API (HTTP-запросы)  |
| `ТаймлогиGitLab`               | Форма для просмотра и управления таймлогами       |
| `НастройкиПользователейGitLab` | Регистр сведений для хранения токенов сотрудников |

### 1.3 Системные требования

- Корпоративный GitLab с поддержкой REST API v4
- Персональный токен API с правами на чтение/запись. На данном этапе поддерживается один АПИ токен на гитлаб сервер, который хранится по ключу PRIVATE_TOKEN в безопасном хранилище (владелец внешняя система - гитлаб сервер)

## 3. Роли пользователей

### 3.1 Сотрудник

**Описание:** Пользователь, который просматривает свои записи времени (timelogs), созданные в других системах (например, Jira), или добавляет свои записи в GitLab.

**Права и возможности:**
- Просмотр своих таймлогов по периоду
- Удаление своих записей времени
- Открытие задач из таймлогов в GitLab

### 3.3 Администратор

**Описание:** Пользователь, который настраивает подключение подсистемы к GitLab (базовый URL, токен аутентификации) и управляет персональными токенами сотрудников.

**Права и возможности:**
- Настройка базового URL GitLab сервера
- Управление токенами доступа к GitLab API

## 4. Администрирование

### 4.1 Требования к правам токена GitLab

Токен аутентификации должен иметь следующие права:
- **read_api** — чтение данных API
- **read_user** — доступ к информации о пользователе
- **read_repository** — чтение репозиториев
- **write_repository** — запись в репозитории (для создания issues)
- **read_issue** — чтение задач (issues)
- **write_issue** — управление задачами
- **read_time_entry** — чтение записей времени (timelogs)
- **write_time_entry** — управление записями времени

### 4.2 Структура регистра сведений «НастройкиПользователейGitLab»

| Атрибут | Тип | Описание |
|---------|-----|----------|
| Сотрудник | СправочникСотрудникиОрганизации | Ссылка на сотрудника |
| ТокенДоступа | Строка | Персональный токен API GitLab |
| БазовыйURL | Строка | URL GitLab сервера (переопределение глобального) |

### 4.3 Глобальные настройки подсистемы

Глобальные настройки хранятся в регистре сведений «НастройкиПодсистемыGitLab»:

| Атрибут | Тип | Описание |
|---------|-----|----------|
| БазовыйURL | Строка | Основной адрес GitLab сервера (например, `https://gitlab.company.com`) |
| ТокенДоступа | Строка | Глобальный токен аутентификации с правами администратора |
| Активен | Булево | Флаг активации подключения |

## 5. Настройка подключения к GitLab

### 5.1 Процедура настройки (UC-06)

**Роль:** Администратор  
**Предусловие:** Подсистема GitLab.mirror установлена, корпоративный GitLab доступен по сети.

**Шаги:**

1. Открыть форму настроек подсистемы GitLab.mirror
2. В поле «БазовыйURL» ввести адрес GitLab сервера (например, `https://gitlab.company.com`)
3. В поле «Токен доступа» ввести токен аутентификации с правами на чтение timelogs и issues
4. Нажать кнопку «Проверить подключение»
5. Система выполняет тестовый запрос к GitLab API для проверки подключения
6. При успешной проверке настройки сохраняются

**Постусловие:** Подсистема подключена к GitLab, готова к работе.

### 5.2 Проверка подключения

Для проверки подключения используется GET-запрос к эндпоинту `/api/v4/user`:

```http
GET /api/v4/user HTTP/1.1
Host: gitlab.company.com
PRIVATE-TOKEN: glpat-your-token-here
```

Успешный ответ (200 OK) подтверждает корректность настроек.

### 5.3 Возможные ошибки при подключении

| Код ошибки | Описание | Решение |
|------------|----------|---------|
| 401 Unauthorized | Неверный токен | Проверить токен и права |
| 403 Forbidden | Токен не имеет достаточных прав | Выдать дополнительные права в GitLab |
| Connection timeout | Невозможно подключиться к GitLab | Проверить сетевую доступность |
| DNS error | Не удалось разрешить адрес | Проверить имя хоста GitLab |

## 6. Настройка токенов сотрудников

### 6.1 Процедура настройки (UC-07)

**Роль:** Администратор  
**Предусловие:** Подсистема GitLab.mirror подключена к GitLab.

**Шаги:**

1. Открыть регистр сведений «НастройкиПользователейGitLab»
2. Создать новый элемент регистра
3. В измерении «Сотрудник» выбрать сотрудника
4. В ресурсе «ТокенДоступа» ввести персональный токен API сотрудника (с правами на чтение/запись timelogs)
5. Сохранить элемент

**Постусловие:** Персональный токен сотрудника настроен, сотрудник может просматривать свои таймлоги.

### 6.2 Создание токена в GitLab для сотрудника

1. Войти в GitLab под аккаунтом сотрудника
2. Перейти: User Settings → Access Tokens
3. Создать токен с правами `read_api`, `read_user`, `read_time_entry`
4. Скопировать сгенерированный токен (формат: `glpat-...`)
5. Передать токен администратору 1С для внесения в регистр сведений

### 6.3 Обновление токенов

Токены GitLab имеют ограниченный срок действия. При истечении срока:

1. Сгенерировать новый токен в GitLab
2. Открыть регистр «НастройкиПользователейGitLab»
3. Заменить значение поля «ТокенДоступа» на новый
4. Сохранить изменения

## 7. Использование для сотрудников

### 7.1 Просмотр своих таймлогов (UC-01)

**Роль:** Сотрудник  
**Предусловие:** Подсистема GitLab.mirror подключена к корпоративному GitLab, токен аутентификации сотрудника настроен.

**Шаги:**

1. Открыть форму «ТаймлогиGitLab»
2. В поле «Сотрудник» выбрать себя (или значение подставится автоматически)
3. В полях «Дата» указать период (конкретную дату или диапазон дат начала/окончания)
4. Нажать «Выполнить поиск»
5. Система отображает таблицу с таймлогами сотрудника за указанный период

**Колонки таблицы результатов:**
| Колонка | Описание |
|---------|----------|
| ID записи | Идентификатор timelog в GitLab |
| Проект | Путь к проекту в GitLab |
| Задача | Номер и описание задачи (issue) |
| Дата/время начала | Дата и время записи времени |
| Длительность | Затраченное время (человеко-читаемый формат) |
| Описание | Описание выполненной работы |
| Веб-ссылка | Ссылка на задачу в GitLab |

### 7.2 Удаление таймлога (UC-02)

**Роль:** Сотрудник  
**Предусловие:** Таймлог сотрудника отображается в таблице формы «ТаймлогиGitLab».

**Шаги:**

1. Выделить строку с нужным таймлогом в таблице результатов
2. Нажать кнопку «Удалить выбранную запись»
3. Подтвердить удаление в диалоговом окне
4. Система отправляет DELETE-запрос на эндпоинт GitLab API
5. Таблица результатов обновляется

**API:** `DELETE /api/v4/projects/{id}/issues/{iid}/timelogs/{timelog_id}`

### 7.3 Открытие задачи в GitLab (UC-03)

**Роль:** Сотрудник  
**Предусловие:** Таймлог отображается в таблице формы «ТаймлогиGitLab».

**Шаги:**

1. Выделить строку с таймлогом
2. Нажать кнопку «Открыть веб-страницу задачи»
3. Система открывает браузер по URL из колонки «Веб-ссылка»

### 7.4 Экспорт в Excel (UC-04)

**Роль:** Сотрудник  
**Предусловие:** Таблица результатов формы «ТаймлогиGitLab» содержит данные.

**Шаги:**

1. Нажать кнопку «Экспорт в Excel»
2. Система формирует табличный документ с данными из таблицы результатов
3. Система предлагает открыть или сохранить файл в формате XLSX

## 8. Использование для менеджеров и руководителей

### 8.1 Просмотр статистики по команде (UC-05)

**Роль:** Менеджер / Руководитель  
**Предусловие:** Токены аутентификации членов команды настроены в регистре сведений «НастройкиПользователейGitLab».

**Шаги:**

1. Открыть форму «ТаймлогиGitLab»
2. В поле «Сотрудник» выбрать члена команды (или не указывать — для просмотра всех)

4. Нажать «Выполнить поиск»
5. Система отображает таблицу с таймлогами за указанный период

| Метрика | Формула | Описание |

## 10. API GitLab и эндпоинты

### 10.1 Справочник эндпоинтов

| Операция | HTTP метод | Эндпоинт | Описание |
|----------|------------|----------|----------|
| Инициализация | GET | `/api/v4/user` | Проверка токена аутентификации |
| Проекты пользователя | GET | `/api/v4/projects?membership=true&state=active` | Список проектов с доступом |
| Задачи пользователя | GET | `/api/v4/users/{user_id}/issues?state=opened` | Назначенные задачи |
| Таймлоги задачи | GET | `/api/v4/projects/{id}/issues/{iid}/timelogs` | Записи времени по задаче |
| Добавить timelog | POST | `/api/v4/projects/{id}/issues/{issue_iid}/time_spent` | Создание записи времени |
| Удалить timelog | DELETE | `/api/v4/projects/{id}/issues/{issue_iid}/timelogs/{timelog_id}` | Удаление записи времени |
| Статистика задачи | GET | `/api/v4/projects/{id}/issues/{issue_iid}/time_stats` | Статистика по времени |
| Таймлоги сотрудника | GET | `/api/v4/users/{user_id}/time_entries?date_on_or_after={d}&date_before={d}` | Записи сотрудника |

### 10.2 Форматы данных

#### Тело запроса создания timelog (POST)

```json
{
    "duration": "1h",
    "spent_at": "2024-01-15T00:00:00Z",
    "summary": "Описание выполненной работы"
}
```

#### Формат ответа получения timelogs (GET)

```json
[
    {
        "id": 123,
        "timelog_id": 456,
        "user": { "name": "Иван Петров" },
        "updated_at": "2024-01-15T10:30:00Z",
        "duration": 3600,
        "comment": "Описание работы"
    }
]
```

#### Коды ответов API

| Код | Описание |
|-----|----------|
| 200 OK | Успешный GET запрос |
| 201 Created | Запись успешно создана |
| 204 No Content | Запись успешно удалена |
| 401 Unauthorized | Неверный токен аутентификации |
| 403 Forbidden | Недостаточно прав |
| 404 Not Found | Ресурс не найден |
| 422 Unprocessable Entity | Ошибка валидации данных |

## 11. Обработка ошибок

### 11.1 Ошибки аутентификации

| Ситуация | Сообщение | Действие |
|----------|-----------|----------|
| Токен истёк | «Ошибка аутентификации GitLab: 401 Unauthorized» | Обновить токен в настройках |
| Токен отозван | «Токен недействителен» | Создать новый токен в GitLab |
| Нет прав | «Доступ запрещён: 403 Forbidden» | Выдать права в GitLab |

### 11.2 Ошибки сети

| Ситуация | Сообщение | Действие |
|----------|-----------|----------|
| Таймаут подключения | «Ошибка подключения к GitLab: таймаут» | Проверить сетевую доступность |
| DNS ошибка | «Не удалось разрешить адрес GitLab» | Проверить имя хоста |
| SSL ошибка | «Ошибка проверки SSL-сертификата» | Добавить сертификат в доверенные |

### 11.3 Ошибки данных

| Ситуация | Сообщение | Действие |
|----------|-----------|----------|
| Timelog не найден | «Timelog {ID} не найден для удаления» | Проверить актуальность ID |
| Задача не найдена | «Задача не найдена в GitLab: 404 Not Found» | Проверить IID задачи |
| Неверный формат даты | «Неверный формат даты: {Дата}» | Исправить формат даты |

> Стратегия частичной синхронизации (выделение групп, цветовые индикаторы 🟢/🟡/⚪ строк) — поведение подсистемы **Таймтрекинг** при синхронизации Листа учёта рабочего времени. Описана в [Таймтрекинг/ДеталиРеализации.md](../Таймтрекинг/ДеталиРеализации.md).
