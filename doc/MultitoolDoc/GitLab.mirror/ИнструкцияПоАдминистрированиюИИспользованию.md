## 1. Общие сведения

### 1.1 Назначение подсистемы

Подсистема **GitLab.mirror** обеспечивает интеграцию 1С с корпоративным GitLab для учёта затраченного рабочего времени (timelogs). Основные функции:

- Просмотр таймлогов сотрудников в GitLab
- Добавление и удаление записей времени
- Экспорт данных в Excel
- Автоматическая синхронизация «Листа учёта рабочего времени» с GitLab
- Формирование отчётов по загрузке команды

### 1.2 Ключевые компоненты

| Компонент | Описание |
|-----------|----------|
| `ФасадИнтеграции` | Центральный компонент диспетчеризации запросов к внешним системам |
| `ПодключениеGitLab` | Обработка подключения к GitLab API |
| `ИнтеграцияGitLab` | Обработка интеграции с GitLab API (HTTP-запросы) |
| `ТаймлогиGitLab` | Форма для просмотра и управления таймлогами |
| `ЛистУчетаРабочегоВремени` | Документ для фиксации рабочего времени |
| `НастройкиПользователейGitLab` | Регистр сведений для хранения токенов сотрудников |

### 1.3 Системные требования

- Корпоративный GitLab с поддержкой REST API v4
- Персональные токены API с правами на чтение/запись issues и timelogs
- 1С:Предприятие с поддержкой HTTP-запросов

## 2. Архитектура подсистемы

### 2.1 Иерархия контекстов обработки

```
┌──────────────────────────────────────────────────────────────┐
│  Обработка «ФасадИнтеграции» — КОНТЕКСТ СЕССИИ ФАСАДА        │
│  (один пользователь, одна сессия, все задачи документа)      │
│                                                              │
│  Контекст: ИдентификаторПользователя, ДатаСинхронизации     │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ Обработка «ПодключениеGitLab» — КОНТЕКСТ ПОДКЛЮЧЕНИЯ  │   │
│  │                                                        │   │
│  │ Контекст: БазовыйURL, ТокенАутентификации             │   │
│  │                                                        │   │
│  │  ┌──────────────────────────────────────────────┐    │   │
│  │  │ Обработка «ИнтеграцияGitLab» — КОНТЕКСТ ИНТ.  │    │   │
│  │  │                                               │    │   │
│  │  │ Контекст: ДанныеПодключения, ТокенАвторизации  │    │   │
│  │  │                                               │    │   │
│  │  │  ┌──────────────────────────────────────┐    │    │   │
│  │  │  │ HTTPКоннектор                        │    │    │   │
│  │  │  │ - ВыполнитьGET()                     │    │    │   │
│  │  │  │ - ВыполнитьPOST()                    │    │    │   │
│  │  │  │ - ВыполнитьDELETE()                  │    │    │   │
│  │  │  └──────────────────────────────────────┘    │    │   │
│  │  └──────────────────────────────────────────────┘    │   │
│  └──────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 Жизненный цикл сессии

1. **Создание ФасадаИнтеграции** — создаётся обработка сессии фасада для одного пользователя
2. **Первый вызов метода фасада** — фасад определяет ТипВнешнейСистемы по `Задача.ВнешняяСистема.ТипСистемы`
3. **Проверка кэша подключений** — если обработка подключения для данного типа системы уже создана в контексте сессии — используется существующая
4. **Создание обработки подключения** — если не найдена, фасад создаёт обработку «Подключение{ТипСистемы}» (контекст подключения)
5. **Создание обработки интеграции** — обработка подключения порождает обработку «Интеграция{ТипСистемы}» (контекст интеграции) с данными подключения и авторизации
6. **Вызов метода интеграции** — фасад делегирует вызов обработке интеграции
7. **Завершение сессии фасада** — все обработки подключения и интеграции уничтожаются

### 2.3 Потоки данных

```
ЛистУчетаРабочегоВремени
        │
        ▼
ФасадИнтеграции (диспетчеризация)
        │
        ▼

        │
        ▼

        ▼

        │

```

## 3. Роли пользователей

### 3.1 Сотрудник

**Описание:** Пользователь, который просматривает свои записи времени (timelogs), созданные в других системах (например, Jira), или добавляет свои записи в GitLab.

**Права и возможности:**
- Просмотр своих таймлогов по периоду
- Удаление своих записей времени
- Открытие задач из таймлогов в GitLab
- Экспорт таймлогов в Excel
- Добавление новых записей времени через «Лист учёта рабочего времени»

### 3.2 Менеджер / Руководитель

**Описание:** Пользователь, который просматривает статистику затраченного времени членов команды на проектах и задачах GitLab для анализа загрузки и отчётности.

**Права и возможности:**
- Просмотр таймлогов любых членов команды
- Анализ распределения времени по проектам и задачам
- Формирование отчётов по загрузке команды
- Экспорт данных в Excel

### 3.3 Администратор

**Описание:** Пользователь, который настраивает подключение подсистемы к GitLab (базовый URL, токен аутентификации) и управляет персональными токенами сотрудников.

**Права и возможности:**
- Настройка базового URL GitLab сервера
- Управление токенами доступа к GitLab API
- Создание и редактирование элементов регистра «НастройкиПользователейGitLab»
- Проверка подключения к GitLab

## 4. Администрирование

### 4.1 Требования к правам токена GitLab

Токен аутентификации должен иметь следующие права:
- **read_api** — чтение данных API
- **read_user** — доступ к информации о пользователе
- **read_repository** — чтение репозиториев
- **write_repository** — запись в репозитории (для создания issues)
- **read_issue** — чтение задач (issues)
- **write_issue** — управление задачами
- **read_time_entry** — чтение записей времени (timelogs)
- **write_time_entry** — управление записями времени

### 4.2 Структура регистра сведений «НастройкиПользователейGitLab»

| Атрибут | Тип | Описание |
|---------|-----|----------|
| Сотрудник | СправочникСотрудникиОрганизации | Ссылка на сотрудника |
| ТокенДоступа | Строка | Персональный токен API GitLab |
| БазовыйURL | Строка | URL GitLab сервера (переопределение глобального) |

### 4.3 Глобальные настройки подсистемы

Глобальные настройки хранятся в регистре сведений «НастройкиПодсистемыGitLab»:

| Атрибут | Тип | Описание |
|---------|-----|----------|
| БазовыйURL | Строка | Основной адрес GitLab сервера (например, `https://gitlab.company.com`) |
| ТокенДоступа | Строка | Глобальный токен аутентификации с правами администратора |
| Активен | Булево | Флаг активации подключения |

## 5. Настройка подключения к GitLab

### 5.1 Процедура настройки (UC-06)

**Роль:** Администратор  
**Предусловие:** Подсистема GitLab.mirror установлена, корпоративный GitLab доступен по сети.

**Шаги:**

1. Открыть форму настроек подсистемы GitLab.mirror
2. В поле «БазовыйURL» ввести адрес GitLab сервера (например, `https://gitlab.company.com`)
3. В поле «Токен доступа» ввести токен аутентификации с правами на чтение timelogs и issues
4. Нажать кнопку «Проверить подключение»
5. Система выполняет тестовый запрос к GitLab API для проверки подключения
6. При успешной проверке настройки сохраняются

**Постусловие:** Подсистема подключена к GitLab, готова к работе.

### 5.2 Проверка подключения

Для проверки подключения используется GET-запрос к эндпоинту `/api/v4/user`:

```http
GET /api/v4/user HTTP/1.1
Host: gitlab.company.com
PRIVATE-TOKEN: glpat-your-token-here
```

Успешный ответ (200 OK) подтверждает корректность настроек.

### 5.3 Возможные ошибки при подключении

| Код ошибки | Описание | Решение |
|------------|----------|---------|
| 401 Unauthorized | Неверный токен | Проверить токен и права |
| 403 Forbidden | Токен не имеет достаточных прав | Выдать дополнительные права в GitLab |
| Connection timeout | Невозможно подключиться к GitLab | Проверить сетевую доступность |
| DNS error | Не удалось разрешить адрес | Проверить имя хоста GitLab |

## 6. Настройка токенов сотрудников

### 6.1 Процедура настройки (UC-07)

**Роль:** Администратор  
**Предусловие:** Подсистема GitLab.mirror подключена к GitLab.

**Шаги:**

1. Открыть регистр сведений «НастройкиПользователейGitLab»
2. Создать новый элемент регистра
3. В измерении «Сотрудник» выбрать сотрудника
4. В ресурсе «ТокенДоступа» ввести персональный токен API сотрудника (с правами на чтение/запись timelogs)
5. Сохранить элемент

**Постусловие:** Персональный токен сотрудника настроен, сотрудник может просматривать свои таймлоги.

### 6.2 Создание токена в GitLab для сотрудника

1. Войти в GitLab под аккаунтом сотрудника
2. Перейти: User Settings → Access Tokens
3. Создать токен с правами `read_api`, `read_user`, `read_time_entry`
4. Скопировать сгенерированный токен (формат: `glpat-...`)
5. Передать токен администратору 1С для внесения в регистр сведений

### 6.3 Обновление токенов

Токены GitLab имеют ограниченный срок действия. При истечении срока:

1. Сгенерировать новый токен в GitLab
2. Открыть регистр «НастройкиПользователейGitLab»
3. Заменить значение поля «ТокенДоступа» на новый
4. Сохранить изменения

## 7. Использование для сотрудников

### 7.1 Просмотр своих таймлогов (UC-01)

**Роль:** Сотрудник  
**Предусловие:** Подсистема GitLab.mirror подключена к корпоративному GitLab, токен аутентификации сотрудника настроен.

**Шаги:**

1. Открыть форму «ТаймлогиGitLab»
2. В поле «Сотрудник» выбрать себя (или значение подставится автоматически)
3. В полях «Дата» указать период (конкретную дату или диапазон дат начала/окончания)
4. Нажать «Выполнить поиск»
5. Система отображает таблицу с таймлогами сотрудника за указанный период

**Колонки таблицы результатов:**
| Колонка | Описание |
|---------|----------|
| ID записи | Идентификатор timelog в GitLab |
| Проект | Путь к проекту в GitLab |
| Задача | Номер и описание задачи (issue) |
| Дата/время начала | Дата и время записи времени |
| Длительность | Затраченное время (человеко-читаемый формат) |
| Описание | Описание выполненной работы |
| Веб-ссылка | Ссылка на задачу в GitLab |

### 7.2 Удаление таймлога (UC-02)

**Роль:** Сотрудник  
**Предусловие:** Таймлог сотрудника отображается в таблице формы «ТаймлогиGitLab».

**Шаги:**

1. Выделить строку с нужным таймлогом в таблице результатов
2. Нажать кнопку «Удалить выбранную запись»
3. Подтвердить удаление в диалоговом окне
4. Система отправляет DELETE-запрос на эндпоинт GitLab API
5. Таблица результатов обновляется

**API:** `DELETE /api/v4/projects/{id}/issues/{iid}/timelogs/{timelog_id}`

### 7.3 Открытие задачи в GitLab (UC-03)

**Роль:** Сотрудник  
**Предусловие:** Таймлог отображается в таблице формы «ТаймлогиGitLab».

**Шаги:**

1. Выделить строку с таймлогом
2. Нажать кнопку «Открыть веб-страницу задачи»
3. Система открывает браузер по URL из колонки «Веб-ссылка»

### 7.4 Экспорт в Excel (UC-04)

**Роль:** Сотрудник  
**Предусловие:** Таблица результатов формы «ТаймлогиGitLab» содержит данные.

**Шаги:**

1. Нажать кнопку «Экспорт в Excel»
2. Система формирует табличный документ с данными из таблицы результатов
3. Система предлагает открыть или сохранить файл в формате XLSX

## 8. Использование для менеджеров и руководителей

### 8.1 Просмотр статистики по команде (UC-05)

**Роль:** Менеджер / Руководитель  
**Предусловие:** Токены аутентификации членов команды настроены в регистре сведений «НастройкиПользователейGitLab».

**Шаги:**

1. Открыть форму «ТаймлогиGitLab»
2. В поле «Сотрудник» выбрать члена команды (или не указывать — для просмотра всех)
3. В полях «Дата» указать период анализа
4. Нажать «Выполнить поиск»
5. Система отображает таблицу с таймлогами за указанный период
6. Проанализировать распределение времени по проектам и задачам

### 8.2 Анализ загрузки команды

Рекомендуемые метрики для анализа:

| Метрика | Формула | Описание |
|---------|---------|----------|
| Загрузка сотрудника | Σ(длительность таймлогов) / Рабочие часы | Процент использования рабочего времени |
| Время по проектам | Группировка по полю «Проект» | Распределение времени между проектами |
| Время по задачам | Группировка по полю «Задача» | Затраты на конкретные задачи |
| Среднее время в день | Σ(длительность) / Кол-во дней | Средняя продолжительность работы |

## 9. Команды интеграции

### 9.1 Структура реквизитов обработки GitLabTimeLog

#### Основные реквизиты:

| Текущее имя | Новое имя | Описание |
|-------------|-----------|----------|
| userID | ПользовательID | ИД пользователя в GitLab |
| After | После | Параметр даты (после) |
| Date | ДатаЗапроса | Дата запроса |
| BaseURL | БазовыйURL | URL GitLab сервера |
| Токен | ТокенДоступа | Токен доступа к GitLab API |

#### Реквизиты табличной части «Таймлог»:

| Текущее имя | Новое имя | Описание |
|-------------|-----------|----------|
| ТаймлогИД | ЗаписьТаймлогИД | ИД записи таймлога в GitLab |
| IssueIID | ЗадачаIID | IID задачи в GitLab |
| Project | ПроектПуть | Путь к проекту |
| Summary | ОписаниеРаботы | Описание работы |
| Duration | ДлительностьСек | Длительность в секундах |
| Date | ДатаРаботы | Дата выполненной работы |

### 9.2 Список команд интеграции

#### GITL-TL-004: Команда инициализации соединения (БАЗОВАЯ)

**Статус:** ✅ Выполнено  
**Описание:** Настройка базового URL и токена аутентификации для GitLab API.  
**Параметры:** БазовыйURL, ТокенДоступа  
**Примечание:** Базовая команда, от которой зависят все остальные

#### GITL-TL-001: Команда получения списка проектов пользователя

**Статус:** ✅ Выполнено  
**Описание:** Получение списка проектов, доступных пользователю в GitLab.  
**Метод API:** `GET /api/v4/projects?membership=true&state=active`  
**Зависимости:** GITL-TL-004

#### GITL-TL-002: Команда получения списка задач (Issues) пользователя

**Статус:** ✅ Выполнено  
**Описание:** Получение списка назначенных задач пользователя.  
**Метод API:** `GET /api/v4/users/{user_id}/issues?state=opened`  
**Зависимости:** GITL-TL-004

#### GITL-TL-003: Команда получения таймлогов для конкретной задачи

**Статус:** ✅ Выполнено  
**Описание:** Получение записей времени, затраченных на конкретную задачу.  
**Метод API:** `GET /api/v4/projects/{id}/issues/{issue_iid}/timelogs`  
**Параметры:** ПроектID, IssueIID, ДатаНач, ДатаКон  
**Зависимости:** GITL-TL-004

#### GITL-TL-005: Команда получения таймлогов сотрудника за период

**Статус:** ✅ Выполнено  
**Описание:** Получение всех записей времени сотрудника за указанный период.  
**Метод API:** `GET /api/v4/users/{user_id}/time_entries`  
**Параметры:** ПользовательID, ДатаНач, ДатаКон  
**Зависимости:** GITL-TL-004

#### GITL-TL-006: Команда добавления записи времени (timelog)

**Статус:** ✅ Выполнено  
**Описание:** Создание новой записи затраченного времени.  
**Метод API:** `POST /api/v4/projects/{id}/issues/{issue_iid}/time_spent`  
**Параметры:** ПроектID, IssueIID, ДлительностьВСекундах, ДатаРаботы, Описание  
**Зависимости:** GITL-TL-004

#### GITL-TL-007: Команда удаления записи времени (timelog)

**Статус:** ✅ Выполнено  
**Описание:** Удаление существующей записи времени.  
**Метод API:** `DELETE /api/v4/projects/{id}/issues/{issue_iid}/timelogs/{timelog_id}`  
**Параметры:** ПроектID, IssueIID, TimelogID  
**Зависимости:** GITL-TL-004

## 10. Фасад интеграции

### 10.1 Назначение

ФасадИнтеграции — центральный компонент подсистемы, обеспечивающий:
- Создание и управление сессиями интеграции
- Диспетчеризацию вызовов к внешним системам по типу системы
- Кэширование обработок подключения и интеграции в рамках сессии

### 10.2 Методы ФасадаИнтеграции

#### Инициализация сессии

| Метод | Описание |
|-------|----------|
| `ИнициализироватьСессию(ИдентификаторПользователя)` | Создаёт сессию фасада для пользователя |
| `ПолучитьИдентификаторПользователя()` | Возвращает ID пользователя из текущей сессии |

#### Работа с записями времени

| Метод | Описание |
|-------|----------|
| `ДобавитьЗаписьОВремени(ВнешняяЗадача, ДлительностьВСекундах, ДатаРаботы, Описание)` | Создаёт timelog во внешней системе |
| `ИзменитьЗаписьОВремени(ИдентификаторЗаписиВремени, Описание)` | Обновляет описание timelog |
| `УдалитьЗаписьОВремени(ИдентификаторЗаписиВремени)` | Удаляет timelog из внешней системы |
| `УдалитьЗаписиОВремениПоДате(ВнешняяЗадача, Дата)` | Удаляет все timelogs за указанную дату |

#### Получение данных

| Метод | Описание |
|-------|----------|
| `ПолучитьСписокЗадач(ТипВнешнейСистемы, ИдентификаторПользователя)` | Возвращает список задач из внешней системы |
| `ПолучитьЗаписиОВремени(ВнешняяСистема, ДатаНач, ДатаКон, Задача)` | Возвращает timelogs за период |

### 10.3 Диспетчеризация вызовов

При вызове метода фасада:

1. Фасад определяет тип внешней системы по `Задача.ВнешняяСистема.ТипСистемы`
2. Проверяет кэш обработок подключения в контексте сессии
3. Если обработка подключения не найдена — создаёт её
4. Обработка подключения порождает обработку интеграции
5. Вызов делегируется обработке интеграции

### 10.4 Обработка задач без интеграции

Если `Задача.ВнешняяСистема.ТипСистемы.ИмеетИнтеграцию = Ложь`:
- Методы фасада возвращают пустое значение
- Вызов обработок интеграции не выполняется
- Запись не синхронизируется с внешними системами

## 11. Лист учёта рабочего времени

### 11.1 Назначение

Документ «ЛистУчетаРабочегоВремени» — ядро подсистемы таймтрекинга. Обеспечивает учёт интервалов рабочего времени работника с автоматической синхронизацией во внешние системы через ФасадИнтеграции.

**Ключевой принцип:** документ не содержит HTTP-вызовов и не знает о конкретных внешних системах. Все операции синхронизации выполняются через `ФасадИнтеграции`.

### 11.2 Состояния документа

| Состояние | Описание |
|-----------|----------|
| Черновик | Документ создан, но рабочий день не начат |
| Активен | Рабочий день ведётся, можно добавлять строки |
| Завершён | Рабочий день завершён, документ зафиксирован |

### 11.3 Методы документа

#### НачатьДень()

Создаёт документ на текущую дату с одной строкой задачи по умолчанию, переводит в состояние «Активен».

**Поведение:**
- Если документ на дату уже существует — переводит в состояние «Активен», строка не дублируется
- Создаётся одна строка с ЗадачаПоУмолчанию и ВремяНачала = 09:00

#### СоздатьСтроку(Задача)

Созёт новую строку табличной части с фиксацией времени окончания предыдущей строки.

**Поведение:**
- ВремяОкончания предыдущей строки устанавливается равным текущему моменту
- ВремяНачала новой строки = ВремяОкончания предыдущей строки
- ТипСтроки определяется автоматически на основе `Задача.ВнешняяСистема.ТипСистемы.ИмеетИнтеграцию`

#### АвтопродлитьПоследнююСтроку()

Обновляет ВремяОкончания последней активной строки на текущую дату и время.

**Поведение:**
- Работает только в состоянии «Активен»
- Игнорируется в состоянии «Завершён»
- Не генерирует ошибку при пустой табличной части

#### ЗавершитьДень()

Фиксирует ВремяОкончания последней строки, переводит документ в состояние «Завершён».

**Поведение:**
- ВремяОкончания последней строки = текущий момент
- Состояние документа = «Завершён»
- Повторный вызов возвращает Ложь

#### Синхронизировать()

Выполняет синхронизацию строк документа со внешними системами через ФасадИнтеграции.

**Алгоритм:**
1. Группирует строки через `СгруппироватьСтрокиДляСинхронизации()`
2. Для каждой группы проверяет наличие актуального ИдентификаторЗаписиВремени
3. При пустом ID — вызывает `ФасадИнтеграции.ДобавитьЗаписьОВремени()`
4. При изменении данных — сначала `УдалитьЗаписьОВремени()`, затем `ДобавитьЗаписьОВремени()`

#### СгруппироватьСтрокиДляСинхронизации()

Группирует последовательные строки с одинаковой задачей для передачи в ФасадИнтеграции.

**Правила группировки:**
- Строки группируются по задачам (одинаковая Задача = одна группа)
- Последовательные строки с разной задачей — разные группы
- Комментарии объединяются через `; ` с уникализацией

### 11.4 Цветовая индикация строк

| Индикатор | Значение |
|-----------|----------|
| 🟢 Зелёный | Запись синхронизирована, данные не менялись |
| 🟡 Жёлтый | Требуется синхронизация (пустой ID или изменены данные) |
| ⚪ Серый | Задача не синхронизируется с внешними системами |

### 11.5 Обновление описания записи

Метод `ОбновитьОписаниеЗаписи(ИдентификаторЗаписиВремени, НовыйКомментарий)`:
- Вызывается при изменении комментария в строке документа
- Через ФасадИнтеграции.ИзменитьЗаписьОВремени() обновляет запись во внешней системе

## 12. API GitLab и эндпоинты

### 12.1 Справочник эндпоинтов

| Операция | HTTP метод | Эндпоинт | Описание |
|----------|------------|----------|----------|
| Инициализация | GET | `/api/v4/user` | Проверка токена аутентификации |
| Проекты пользователя | GET | `/api/v4/projects?membership=true&state=active` | Список проектов с доступом |
| Задачи пользователя | GET | `/api/v4/users/{user_id}/issues?state=opened` | Назначенные задачи |
| Таймлоги задачи | GET | `/api/v4/projects/{id}/issues/{iid}/timelogs` | Записи времени по задаче |
| Добавить timelog | POST | `/api/v4/projects/{id}/issues/{issue_iid}/time_spent` | Создание записи времени |
| Удалить timelog | DELETE | `/api/v4/projects/{id}/issues/{issue_iid}/timelogs/{timelog_id}` | Удаление записи времени |
| Статистика задачи | GET | `/api/v4/projects/{id}/issues/{issue_iid}/time_stats` | Статистика по времени |
| Таймлоги сотрудника | GET | `/api/v4/users/{user_id}/time_entries?date_on_or_after={d}&date_before={d}` | Записи сотрудника |

### 12.2 Форматы данных

#### Тело запроса создания timelog (POST)

```json
{
    "duration": "1h",
    "spent_at": "2024-01-15T00:00:00Z",
    "summary": "Описание выполненной работы"
}
```

#### Формат ответа получения timelogs (GET)

```json
[
    {
        "id": 123,
        "timelog_id": 456,
        "user": { "name": "Иван Петров" },
        "updated_at": "2024-01-15T10:30:00Z",
        "duration": 3600,
        "comment": "Описание работы"
    }
]
```

#### Коды ответов API

| Код | Описание |
|-----|----------|
| 200 OK | Успешный GET запрос |
| 201 Created | Запись успешно создана |
| 204 No Content | Запись успешно удалена |
| 401 Unauthorized | Неверный токен аутентификации |
| 403 Forbidden | Недостаточно прав |
| 404 Not Found | Ресурс не найден |
| 422 Unprocessable Entity | Ошибка валидации данных |

## 13. Обработка ошибок

### 13.1 Ошибки аутентификации

| Ситуация | Сообщение | Действие |
|----------|-----------|----------|
| Токен истёк | «Ошибка аутентификации GitLab: 401 Unauthorized» | Обновить токен в настройках |
| Токен отозван | «Токен недействителен» | Создать новый токен в GitLab |
| Нет прав | «Доступ запрещён: 403 Forbidden» | Выдать права в GitLab |

### 13.2 Ошибки сети

| Ситуация | Сообщение | Действие |
|----------|-----------|----------|
| Таймаут подключения | «Ошибка подключения к GitLab: таймаут» | Проверить сетевую доступность |
| DNS ошибка | «Не удалось разрешить адрес GitLab» | Проверить имя хоста |
| SSL ошибка | «Ошибка проверки SSL-сертификата» | Добавить сертификат в доверенные |

### 13.3 Ошибки данных

| Ситуация | Сообщение | Действие |
|----------|-----------|----------|
| Timelog не найден | «Timelog {ID} не найден для удаления» | Проверить актуальность ID |
| Задача не найдена | «Задача не найдена в GitLab: 404 Not Found» | Проверить IID задачи |
| Неверный формат даты | «Неверный формат даты: {Дата}» | Исправить формат даты |

### 13.4 Стратегия частичной синхронизации

При синхронизации нескольких групп записей:
- Успешные группы помечаются 🟢 зелёным индикатором
- Группы с ошибками помечаются 🟡 жёлтым индикатором
- Исключение не генерируется — пользователь видит результат каждой группы
- Повторная синхронизация возможна для групп с жёлтым индикатором
