        Смотрит, есть ли уже в GitLab timelog за эту дату и этот Issue (можно хранить соответствие локально, либо проверять через GET /projects/:id/issues/:issue_iid/timelogs).

        Если есть – удаляет старые и создаёт новый с суммированным временем и объединённым summary. Это даёт «корректируемость» — работник поправил лист дня и синхронизировал заново, старые данные перезаписываются.

        Если нет – просто создаёт новый timelog.

    Специальная задача «Неопределённая работа» – для неё можно создать реальный Issue в GitLab (например, в служебном проекте), куда будет списываться время до уточнения. Когда работник меняет Issue в строке, клиент удаляет timelog из этой заглушки и переносит время в нужный Issue. Так аналитики увидят, что было что‑то нераспределённое, если работник не исправил до конца учётного периода.

Обед – время не синхронизируется, никаких записей не создаётся.
4. Почему это удобно работнику (и только ему)

    Никакого старт/стоп — достаточно один раз утром настроить лист дня, а дальше он просто живёт: текущая задача продлевается автоматически, а переключение – это вставка новой строки (можно горячей клавишей).

    Естественная правка в конце дня – работник просматривает лист, исправляет формулировки, уточняет задачи, объединяет/разделяет строки. Все изменения на лету.

    Время «забытых» кусков не теряется – всегда есть интервал непрерывности, и незаполненное время явно висит как «Не указано».

    Комментарии пишутся по ходу дела коротко, а в конце собираются в осмысленный итог без мусора.

    Синхронизация в GitLab – одна кнопка, после которой все данные для отчётов уже на месте.

5. Техническая реализация (концепт)

    Локальное хранение – JSON/файл или легковесная БД (SQLite) с записями на каждый день: дата, массив строк {start, end, issue_id (или null), comment, is_break}.

    Автосохранение раз в минуту, чтобы не потерять при сбое.

    Фоновый поток – раз в 5 минут обновляет end последней строки, если она активна (работник не поставил явный конец).

    Модуль синхронизации – по команде или при закрытии дня вызывает GitLab API, группирует, создаёт/обновляет timelog’и.

    Сопоставление строк и timelog’ов – можно хранить в локальной БД идентификаторы созданных записей для быстрого обновления.

Подсистемы

2. Документ «ЛистУчетаРабочегоВремени»
Реквизиты шапки

    Дата (тип Дата, состав даты – «Дата») – дата, на которую составляется лист.

    ВремяНачалаДня (Дата, состав – «Время») – точка отсчёта, по умолчанию 9:00.

    ВремяОкончанияДня (Дата, состав – «Время») – завершающая граница, изначально пусто, пока работник не завершил день.

    Автопродление (Булево) – включён ли режим автоматического продления последней строки (по умолчанию Истина).

    ПериодАвтопродления (Число, целое, секунд) – интервал, с которым обновляется время окончания последней строки, например 300 (5 минут).

    Состояние (ПеречислениеСсылка.СостоянияЛиста) – Черновик, Активен, Завершён, Синхронизирован.

    ИдентификаторПользователя – ссылка на справочник Пользователи (или просто строка для GitLab user ID).

Табличная часть «Строки»

    НомерСтроки (Число) – порядок.

    ВремяНачала (Дата, время) – вычисляется автоматически: для первой строки = ВремяНачалаДня, для остальных = ВремяОкончания предыдущей строки. Пользователь может редактировать, но при изменении система корректирует соседние строки, сохраняя непрерывность.

    ВремяОкончания (Дата, время) – для всех строк, кроме последней, равно ВремяНачала следующей; для последней – либо введено вручную, либо (если Активен) периодически обновляется до ТекущаяДата().

    Ишью (Строка или ссылка на внешний источник) – можно хранить в виде строки project_id:issue_iid или использовать отдельный справочник «ЗадачиGitLab», который синхронизируется с назначенными Issues.

    ТипСтроки (ПеречислениеСсылка.ТипыСтрокЛиста) – Рабочая, Обед, Неопределенная. Визуально Обед выделяется, Неопределенная – подсвечивается как требующая уточнения.

    Комментарий (Строка) – короткое описание работы в этом интервале.

Дополнительная табличная часть для хранения соответствия строкам GitLab (может быть невидимой, заполняется при синхронизации)

    TimelogID (Число или Строка) – идентификатор записи в GitLab.

    ДатаСинхронизации (Дата) – когда была отправлена эта группа строк.

Но лучше хранить это в регистре сведений «СоответствияСтрокTimelog», чтобы не засорять документ.
3. Регистры (опционально)

    Регистр сведений «НастройкиПользователяGitLab» – периодический, хранение токена, URL, ID заглушки.

    Регистр сведений «СоответствияСтрокTimelog» – измерения: Документ, НомерСтроки (начальная строка группы); ресурсы: TimelogID, IssueID. Позволяет быстро найти, какие строки уже синхронизированы.

4. Логика работы с документом (удобство работника)
Создание нового листа

    На форме «Начать день» – создаётся документ на текущую дату, одна строка: ВремяНачала = ВремяНачалаДня, ТипСтроки = Неопределенная, Ишью пусто. Документ переводится в состояние «Активен», запускается фоновое задание автопродления.

Автопродление

    Пока документ активен, серверный регламент (или обработчик ожидания на форме) раз в ПериодАвтопродления обновляет ВремяОкончания последней строки = ТекущаяДата(). Это делается безусловно, если не вмешался пользователь (не нажал «Стоп»).

    На форме клиента можно отображать таймер, показывающий продолжительность текущего интервала.

Вставка новой строки (переключение задачи)

    Пользователь нажимает «Новая задача» (или Ctrl+Enter) – в табличную часть добавляется новая строка после текущей (или перед последней, если последняя активна).

    У текущей строки ВремяОкончания фиксируется = ТекущаяДата().

    Новая строка получает ВремяНачала = этому времени, ВремяОкончания изначально = ВремяНачала (потом автопродление обновит). ТипСтроки = Неопределенная, предлагается ввести Ишью и комментарий.

    Если пользователь вставляет строку в середину (например, забыл записать перерыв), он может указать вручную время – система проверит непрерывность и, если нужно, сдвинет соседние строки. Алгоритм: пересчитать времена так, чтобы интервал [ВремяНачалаДня; ВремяОкончанияДня] был покрыт без разрывов, корректируя время начала/окончания соседних строк пропорционально или сдвигом.

Указание задачи и типа строки

    У строки можно выбрать Ишью из списка (заполняется асинхронным запросом к GitLab API – назначенные на пользователя открытые Issues). Если Ишью не указано, тип автоматически становится «Неопределенная», иначе – «Рабочая».

    Обед – выбирается из выпадающего списка типов, или просто специальная кнопка «Обед». При этом ВремяОкончания не обновляется автоматически? Лучше: когда начинается обед, пользователь жмёт «Обед», создаётся строка с типом Обед, Ишью пусто, начальное время – текущее, конечное – пока не указано, но автопродление для неё не применяется (можно отключить для строк с типом Обед). Пользователь вручную заканчивает обед, добавив следующую рабочую строку.

Завершение дня

    Пользователь нажимает «Завершить день»: в последней строке ВремяОкончания фиксируется = ТекущаяДата(), состояние меняется на «Завершён». Автопродление останавливается.

    После этого можно вручную редактировать строки, комментарии, уточнять задачи. Состояние остаётся «Завершён», но флаг «Синхронизирован» сбрасывается (если ранее был).

    Затем доступна кнопка «Синхронизировать с GitLab».

6. Синхронизация с GitLab (формирование timelog'ов)
Когда запускается

    По кнопке «Синхронизировать» на форме документа.

    Может быть автоматически при завершении дня, если настроено.

Алгоритм синхронизации (выполняется на сервере 1С)

    Выбрать строки документа, у которых ТипСтроки = Рабочая (или Неопределенная, если настроено), исключая Обед.

    Группировка подряд идущих строк с одинаковым Ишью. Подряд – значит, что между ними нет строк с другим Ишью (Неопределенная считается отдельной задачей). Если Ишью не указан, он заменяется на ID заглушки «Неопределенная работа» (специальный Issue в GitLab).
    Группировка выполняется с учётом порядка строк: если две Рабочие строки с одним Issue разделены Обедом, они попадут в разные группы (прерывание).
    В итоге получаем массив групп: {IssueID, СписокСтрок, СуммарнаяДлительность, ИтоговыйКомментарий}.

    Формирование итогового комментария:

        Собрать все непустые комментарии строк группы.

        Удалить дубликаты (можно просто через уникальный массив).

        Объединить через точку с запятой или перенос строки, можно с префиксом времени, например: «09:00-10:25 Правки макета; 10:25-11:00 Правки макета после созвона» – но это опционально.

        Если все комментарии пусты, summary = "".

    Для каждой группы:

        Определить дату работы – из даты строк (скорее всего одна дата, если работа не переходит через полночь; если переходит – можно разбить или создавать несколько timelog'ов с разными spent_at, но упростим: берём spent_at = Дата документа + ВремяНачала первой строки группы (без даты). Время должно быть в UTC, GitLab сам преобразует).

        Проверить, есть ли уже синхронизированные записи для этой группы (по данным регистра соответствия). Если есть – вызвать УдалитьTimelog для каждого старого ID.

        Вызвать ДобавитьЗатраченноеВремя(IssueID, СуммарнаяДлительностьВСекундах, spent_at, ИтоговыйКомментарий).

        Сохранить новый TimelogID в регистре соответствия, связав с первой строкой группы (или с документом+идентификатор группы).

    Обработка неопределённых задач:
    Если строка осталась с типом Неопределенная и Issue не указан, списываем время на Issue-заглушку. Позже, когда работник укажет конкретную задачу и пересинхронизирует, система удалит запись из заглушки и создаст в нужной задаче.

    После успешной синхронизации – установить состояние документа «Синхронизирован», запретить редактирование строк (опционально, можно разрешить, но тогда сбросить флаг синхронизации и потребовать пересинхронизации).

Обработка ошибок

    Если GitLab недоступен, выдать сообщение, синхронизацию не проводить.

    Можно хранить лог синхронизации в регистре.

7. Изоляция библиотеки GitLab

    Все HTTP-вызовы сосредоточены в общем модуле GitLabAPI. Он не ссылается на документы или справочники конфигурации. Принимает простые параметры (URL, токен, issue_iid, duration, summary и т.д.) и возвращает структуры данных (числа, строки, таблицы значений).

    Модуль РаботаСGitLab получает данные из документа (строки, суммы), но не содержит HTTP-логики. Вызывает методы GitLabAPI и обрабатывает результаты. Таким образом, если потребуется заменить GitLab на Jira, достаточно переписать GitLabAPI, сохранив интерфейс модуля РаботаСGitLab.

    Документ «ЛистУчетаРабочегоВремени» взаимодействует только с РаботаСGitLab через вызовы его экспортных процедур («СинхронизироватьЛист», «ПолучитьСписокЗадач»). Никаких HTTP-деталей.

8. Дополнительные удобства (оперативность ввода)

    Горячие клавиши: Ctrl+N – новая строка (переключение задачи), Ctrl+Shift+O – обед, Ctrl+S – синхронизировать.

    Автозаполнение Ишью: при вводе текста в поле «Ишью» можно организовать асинхронный поиск по назначенным задачам (используя фоновый вызов ПолучитьНазначенныеЗадачи при открытии формы и фильтрацию на клиенте). Это быстро и не требует постоянных запросов к API.

    Предупреждение о длинных интервалах без задачи: если тип «Неопределенная» сохраняется дольше 30 минут, подсвечивать строку.

    Таймер текущей задачи на форме – отображение длительности активной строки в реальном времени (через вычисление на клиенте по таймеру).

9. Итоговый workflow

    Утром работник открывает 1С, жмёт «Начать день» – создаётся новый документ.

    В течение дня он добавляет строки, меняет задачи, вводит короткие комментарии. Последняя строка сама растёт.

    В конце дня жмёт «Завершить день», затем редактирует формулировки, уточняет задачи.

    Для аналитиков в GitLab доступна стандартная отчётность по затраченному времени в разрезе Issues и проектов, без привязки к 1С.

1. Справочник «ВнешниеЗадачи» (назовём его так для ясности)

Он будет хранить задачи из любых систем (GitLab, Jira, Trello, …). Это единый реестр рабочих элементов, с которым взаимодействует работник.
Реквизиты справочника

    Наименование – строка, краткое описание задачи (может обновляться при синхронизации с внешней системой).

    ВнешнийИдентификатор – строка, уникально идентифицирующая задачу во внешней системе (например, namespace/project_id:issue_iid для GitLab, PROJ-123 для Jira). Формат хранения свободный, но мы договоримся о шаблоне, чтобы уметь его разбирать.

    ТипВнешнейСистемы – перечисление (GitLab, Jira, …) – определяет, через какой API работать.

    ТипЗадачи – перечисление (Обычная, Обед, Перерыв, Служебная). Служебные задачи (Обед, Перерыв) не синхронизируются с внешним трекером.

    СсылкаНаПроект – строка (необязательно) – для быстрого доступа к веб-интерфейсу.

    Активна – булево, для фильтрации устаревших задач.

    ДатаПоследнейСинхронизации – дата, когда обновлялось описание из внешней системы.

    Ответственный – может быть ссылкой на справочник «Пользователи» 1С, для персонализации списков.

Константы подсистемы тайм-трекинга

    ЗадачаПоУмолчанию – ссылка на элемент справочника с типом «Обычная» (например, «Нераспределённая работа»). Она будет подставляться, когда работник не выбрал конкретную задачу.

    ЗадачаОбед – ссылка на элемент с типом «Обед». Может быть создан один экземпляр, который используется для всех пользователей.

    При желании можно также создать константу ЗадачаПерерыв и т.п.

Все эти константы вынесены в подсистему «УчетРабочегоВремени» и не затрагивают интеграционную библиотеку.
2. Документ «ЛистУчетаРабочегоВремени» – изменения

В табличной части «Строки» вместо поля «Ишью» теперь:

    Задача – ссылка на справочник «ВнешниеЗадачи» (реквизит табличной части).

    ТипСтроки – вычисляемое поле (не хранится физически) или заполняется автоматически при выборе задачи на основании её ТипаЗадачи.
    Можно и хранить для производительности, но тогда нужно обеспечить непротиворечивость (автоматическое обновление при смене задачи). Для гибкости оставим вычисляемым: при каждом обращении берём у Задачи.ТипЗадачи. Если задача не указана, подразумеваем тип «Неопределенная» (но такая строка всё равно будет ссылаться на ЗадачуПоУмолчанию при синхронизации, см. ниже).

Поведение:

    При создании новой строки (переключение задачи) – поле «Задача» пустое, но под капотом она временно считается ссылающейся на ЗадачуПоУмолчанию (для целей автопродления и подсветки). Пользователь может оставить пустым или выбрать из выпадающего списка.

    При вставке обеда – работник просто выбирает задачу «Обед» (она может быть первой в списке или по горячей клавише). Тип задачи «Обед» автоматически даст строке признак, что она не участвует в синхронизации.

    При завершении дня, если в каких-то строках задача осталась пустой, они перед синхронизацией автоматически связываются с ЗадачейПоУмолчанию (это можно сделать явно при сохранении документа). Таким образом, всё время будет распределено.

        ДобавитьЗатраченноеВремя(Задача, ДлительностьВСекундах, ДатаРаботы, Описание) – по ТипуВнешнейСистемы и ВнешнемуИдентификатору вызывает нужный API-метод.

3.3. Работа с задачами из нескольких систем

Справочник «ВнешниеЗадачи» может наполняться как вручную, так и автоматически (через регламентное задание, подтягивающее открытые задачи из GitLab по токену пользователя). Для оперативной работы достаточно ручного добавления наиболее частых задач, либо быстрого поиска при вводе: форма ввода поля «Задача» делает асинхронный запрос к Фасаду ПолучитьСписокЗадач для выбранной системы (или всех сразу) и показывает подсказки. При выборе новой задачи, которой ещё нет в справочнике, система может автоматически создать её (с заполнением ВнешнийИдентификатор, ТипВнешнейСистемы) после подтверждения пользователя.
4. Обновлённый алгоритм синхронизации (группировка и выгрузка)

При нажатии «Синхронизировать» на форме документа выполняются шаги:

    Подготовка данных: проходим по строкам документа, для каждой строки определяем фактическую задачу:

        Если Задача заполнена – используем её.

        Если пусто – подставляем ЗадачаПоУмолчанию (из константы).

        Строки, у которых задача имеет тип «Обед» (или «Перерыв»), игнорируем.

    Группировка последовательных строк с одинаковой задачей (ссылкой на элемент справочника). Между ними не должно быть строк с другой задачей (кроме обедов, которые прерывают группу).
    Внутри группы вычисляем:

        Суммарная длительность = сумма (ВремяОкончания - ВремяНачала) всех строк группы.

        Итоговый комментарий: собираем уникальные непустые комментарии строк (удаляем дубли) и объединяем через символ перевода строки или точку с запятой.

    Для каждой группы:

        Из элемента справочника «Задача» получаем ТипВнешнейСистемы и ВнешнийИдентификатор.

        Определяем spent_at = Дата документа + ВремяНачала первой строки группы.

        Вызываем ФасадВнешнихСистем.ДобавитьЗатраченноеВремя(Задача, СуммарнаяДлительность, spent_at, ИтоговыйКомментарий).
        Внутри фасада для GitLab будет вызван GitLabAPI с параметрами: project_id, issue_iid, duration, summary.

        Фасад возвращает идентификатор созданной записи (TimelogID) в формате, специфичном для системы (строка/число). Сохраняем его в регистр соответствия (измерение: Документ, Группа (например, первая строка группы), ТипСистемы; ресурс: ВнешнийIDЗаписи).

    Обработка уже существовавших записей: перед добавлением можно удалить старые записи по данной задаче и дате, чтобы обеспечить идемпотентность. Для этого фасад предоставляет метод УдалитьЗатраченноеВремяПоДате(Задача, Дата), который получает список timelog'ов и удаляет их. Это позволит безболезненно пересинхронизировать день после правок.

После успешной синхронизации документ помечается состоянием «Синхронизирован».
5. Удобство работника (детали интерфейса)

    Выбор задачи – поле с выпадающим списком, который динамически загружается при активации. Можно реализовать через список «Последние использованные» + поиск по подстроке с запросом к Фасаду (по всем системам сразу). Часто используемые задачи (свои активные) кешируются на форме.

    Горячие клавиши:

        Ctrl+Shift+O – вставить строку с задачей «Обед» (текущая фиксируется, начинается обед).

        Ctrl+N – новая строка с пустой задачей (подразумевается переход к следующей работе).

    Подсветка строк: если строка более 15 минут с типом «Неопределенная» (пустая задача), подсвечивается жёлтым. Если задача – Обед – выделяется серым фоном.

    Автопродление работает только для строк с задачей, не являющейся обедом. При переходе на обед автопродление последней строки останавливается (пользователь должен явно завершить обед новой строкой).

        Справочник «ВнешниеСистемы» (уже экземпляры: «Наш GitLab», «Внутренний портал») – содержит URL, тип, настройки аутентификации (но без привязки к пользователю).

    Задачи (Issue) – в справочнике «ВнешниеЗадачи» обязательно поле ВнешняяСистема (ссылка на элемент справочника «ВнешниеСистемы»). Если задачи локальные (Обед, Перерыв), для них создаётся элемент «ВнешниеСистемы» с типом, у которого не указана интеграция (или пустым). Больше не нужно специальных перечислений «Обед» – просто задача в специальной системе без интеграции.

    Хранение Timelog ID: прямо в табличной части документа «ЛистУчетаРабочегоВремени» в поле ИдентификаторЗаписиВремени (строка). Синхронизация проставляет его в строках документа, сгруппированных по задаче. При редактировании строк система проверяет соответствие: если задача изменилась или суммарное время поменялось, идентификатор сбрасывается (или строка подсвечивается), требуя пересинхронизации.

    Подсистема GitLab обогащается формой для работы с таймлогами напрямую: просмотр за дату, за период, возможно ручная корректировка.

2. Обработка соответствия timelog'ов в строках

После группировки и успешной синхронизации в GitLab для каждой группы строк с одинаковой задачей получаем timelog_id. Этот идентификатор записывается во все строки, вошедшие в группу. Таким образом, видно, какие именно интервалы объединены в одну запись.

При любом изменении в строках (ручная правка времени, изменение задачи, удаление/вставка строк) для всех затронутых строк поле ИдентификаторЗаписиВремени сбрасывается (или помечается как неактуальное). На форме строки с неактуальными идентификаторами подсвечиваются (например, жёлтым фоном в колонке «Синхр.»).

Синхронизация при следующем запуске:

    Найти все строки с непустым ИдентификаторомЗаписиВремени, сгруппировать по этому идентификатору – это группы, которые были отправлены ранее.

    Сравнить суммарное время и задачу в текущей группе с тем, что было. Если изменилось – удалить старый timelog (или обновить, если API позволяет, но лучше удалить и создать новый).

    Для новых или изменённых групп создать новые записи.

    После успешной синхронизации обновить ИдентификаторЗаписиВремени во всех строках соответствующих групп.

4. Алгоритм синхронизации с учётом новых требований

Подготовка:

    Получить строки документа, исключая те, у которых задача ссылается на ВнешнююСистему с ТипСистемы.ИмеетИнтеграцию = Ложь (Обед, локальные задачи).

    Для каждой строки, где Задача пуста, подставить ЗадачуПоУмолчанию (но она тоже без интеграции, поэтому время на неё останется локальным, либо можно создать специальную задачу в GitLab для неопределённого времени – на усмотрение).

Группировка:

    Группируем последовательные строки с одинаковой задачей (ссылкой). Если задача имеет интеграцию, это группа для синхронизации.

    Для каждой группы считаем суммарное время и объединённый комментарий (уникальные непустые строки через разделитель).

    Определяем spent_at = Дата документа + ВремяНачала первой строки группы (время UTC для API, 1С умеет преобразовывать).

Сравнение с существующими:

    Смотрим на идентификаторы в строках группы. Если есть одинаковый непустой идентификатор во всех строках группы (и он совпадает), считаем, что группа ранее синхронизирована как одна запись. Иначе – новая.

    Для ранее синхронизированной группы проверяем, не изменились ли задача или итоговое время по сравнению с сохранёнными (можно хранить контрольную сумму в дополнительном поле или просто всегда пересоздавать, удалив старый timelog). Для простоты – всегда удаляем старый timelog по идентификатору и создаём новый.

Вызов API:

    Используем фасад ВнешниеСистемы.ДобавитьЗатраченноеВремя(Задача, Длительность, spent_at, Описание).

    Внутри фасад определяет по Задача.ВнешняяСистема.ТипСистемы нужный API-модуль (GitLabAPI) и вызывает его, передавая ВнешняяСистема.БазовыйURL, Задача.ВнешнийИдентификатор и параметры.

    GitLabAPI разбирает ВнешнийИдентификатор на project_id и issue_iid, делает POST /projects/:id/issues/:issue_iid/time_spent.

    Получает ID нового timelog (возвращается в ответе API) и возвращает его в фасад, а тот – в документ.

Обновление строк:

    Записываем полученный идентификатор во все строки группы.

    Строки, которые не попали в синхронизацию (Обед), остаются с пустым идентификатором.

Обработка ошибок:

    Если для какой-то задачи API вернул ошибку (например, нет прав или задача не найдена), формируем сообщение и не сбрасываем старые идентификаторы для этой группы. Помечаем строки как «ошибка синхронизации».

5. Форма документа и удобство

    Поле Задача – выпадающий список с возможностью поиска по первым буквам. При открытии списка загружаются активные задачи (можно кешировать). При необходимости – асинхронный запрос к API внешней системы для подгрузки новых задач (но это редко, в основном справочник наполняется заранее).

    Подсветка строк:

        Зелёный индикатор – синхронизировано (идентификатор непуст, и данные не менялись).

        Жёлтый – требуется синхронизация (идентификатор пуст или данные изменились).

        Серый – строка без интеграции (Обед).

    Кнопка «Синхронизировать» – активна, когда есть изменения. Выполняет описанный алгоритм.

    Двойной клик на строке с заполненным идентификатором может открывать веб-страницу задачи или, возможно, форму просмотра таймлога (если реализована).

2. Как работает связь со строками и отслеживание изменений

    При синхронизации группа строк с одинаковой задачей получает один timelog_id, который записывается в каждую строку этой группы.

    Если пользователь изменил в любой из этих строк задачу, время или удалил/добавил строки — для всех затронутых строк поле ИдентификаторЗаписиВремени сбрасывается (или помечается как неактуальное). На форме такие строки подсвечиваются (например, жёлтым индикатором).

    При следующей синхронизации: для групп, где идентификатор сохранился и данные не изменились, ничего не делаем. Для групп со сброшенным идентификатором (или изменившимся) — удаляем старый timelog через API (по сохранённому где-то соответствию) и создаём новый.

3. Алгоритм синхронизации с учётом хранения ID в строках

    Исключаем строки, у которых Задача.ВнешняяСистема.ТипСистемы.ИмеетИнтеграцию = Ложь (обеды, локальные). Для них синхронизация не выполняется.

    Группируем оставшиеся строки по последовательности с одинаковой Задача.

    Для каждой группы:

        Суммируем длительности.

        Формируем summary: уникальные непустые комментарии через ; .

        spent_at = Дата документа + ВремяНачала первой строки группы.

    Проверяем наличие непустого идентификатора в любой строке группы. Если во всех строках группы одинаковый непустой идентификатор, считаем, что группа ранее синхронизирована. Сравниваем контрольную сумму (можно хранить в доп. реквизите или просто всегда пересоздавать). Для простоты: всегда удаляем старый timelog по идентификатору и создаём новый — это гарантирует актуальность.

    Вызываем ФасадВнешнихСистем.ДобавитьЗатраченноеВремя(), передавая задачу, длительность, дату и описание. Фасад определяет по ВнешняяСистема.ТипСистемы нужный API-модуль (GitLabAPI) и вызывает его.

    Полученный new_timelog_id записываем во все строки группы.

    Ошибки: если API возвращает ошибку, не сбрасываем старые идентификаторы, выводим сообщение, строки помечаем как «ошибка».

6. Интерфейс работника (документ)

    Поле Задача — выпадающий список с поиском по началу строки. При открытии показывает активные задачи (кешируется). Рядом кнопка «+», чтобы быстро создать новую задачу в справочнике, если её ещё нет.

    Индикаторы строк:

        Зелёный — синхронизировано и актуально.

        Жёлтый — требуется синхронизация (идентификатор сброшен или данные изменились).

        Серый — не синхронизируется (Обед, локальная задача).

    Кнопка «Синхронизировать» запускает алгоритм. После завершения обновляет индикаторы.

    Двойной щелчок на строке с заполненным идентификатором может открывать веб-страницу задачи или форму таймлога.
