1. Разделение ответственности (слои)

Всю библиотеку предлагаю разделить на четыре слоя:

    Транспортный адаптер – низкоуровневое выполнение HTTP-запросов, управление соединениями, заголовками, сжатием.

    Адаптер аутентификации – получение/обновление токенов, добавление их в запрос.

    Сериализатор/десериализатор – преобразование типов 1С ↔ JSON/XML/другое.

    Клиент API (доменный сервис) – выразительные методы вида СоздатьЗаказ(), ПолучитьСтатус(), работающие с доменными структурами, а не с HTTP-деталями.

Каждый слой реализуется отдельным модулем/обработкой с чётко определённым интерфейсом. Это позволяет тестировать слои изолированно и заменять реализацию без переписывания логики.

3. Структура метаданных (пример)

Рекомендую использовать обработки как объекты-сервисы (а не простые общие модули), потому что они позволяют хранить внутреннее состояние (например, текущий токен) и легко заменяются в тестах целиком.

4. Обеспечение тестопригодности

Главный принцип – всё, что касается ввода-вывода, параметризуется:

    HTTP-клиент передаётся в доменный сервис извне, а не создаётся внутри. В продуктивном коде это реальный модуль, в тесте – заглушка.

    Дата/время можно получать через параметр, а не через ТекущаяДата(), если это влияет на логику (например, проверка срока токена).

    Для заглушек удобно использовать временное хранилище или структуру, где записан ожидаемый ответ.

Пример подмены в тесте (Vanessa Automation / xUnitFor1C):

КлиентAPI = Обработки.КлиентВнешнейСистемы.Новый(

5. Производительность без ущерба архитектуре

Гексагональная архитектура не должна вести к излишним накладным расходам, если учесть несколько моментов:

    Повторное использование HTTP-соединения – в адаптере транспорта держим пул соединений на основе доменного имени, явно закрываем через метод Освободить(). Не создаём новый объект HTTPСоединение на каждый запрос.

    Кэширование сериализованных метаданных – если API требует многократного преобразования одних и тех же структур, сериализатор может кэшировать соответствие полей.

    Асинхронная обработка – длительные REST-вызовы стоит оборачивать в фоновые задания. Для этого в транспорте выделяем асинхронный адаптер, который ставит задачу и возвращает идентификатор, либо используем асинхронные методы HTTPСоединение.ОтправитьАсинхронно() (если доступны).

    Таймауты и повторные попытки – настраиваются в адаптере транспорта; доменный слой даже не подозревает о них. Используем экспоненциальную задержку с ограничением общего времени.

    Пакетная работа – если требуется отправить много объектов, доменный сервис предоставляет методы для работы с коллекциями, а адаптер транспорта может использовать компрессию (gzip).

    Ленивое получение токена – аутентификатор запрашивает токен при первом вызове и кэширует его до истечения срока, но кэш хранится внутри адаптера, изолированно.

7. Итоговая выгода

    Полная модульность – можно заменить HTTP-клиент с WinInet на libcurl, поменять JSON на XML, перейти с OAuth на взаимный TLS, не трогая бизнес-логику.

    Производительность – изолированные адаптеры позволяют централизованно управлять кэшированием, таймаутами и пулами соединений, не дублируя код.

    Прозрачная поддержка – разработчик доменного метода видит только чистую логику работы с данными, без строк HTTPСоединение.Вызвать.

Такой подход превращает интеграцию в 1С из набора неструктурированных скриптов в полноценный SDK, который легко расширять и сопровождать.

При этом нужно избежать лишних запросов к БД для получения этих идентификаторов. Нужно предложить решение, сохраняющее архитектуру и производительность.

Основные моменты:

    Доменный сервис (обработка "КлиентGitLab_Timesheets") должен предоставлять методы, которые принимают и возвращают бизнес-сущности (Сотрудник, НоменклатурнаяГруппа, ЗадачаGitLab (справочник), Дата, Комментарий).

    Внутри сервиса нужно преобразовывать бизнес-сущности в идентификаторы GitLab и обратно.

Мы должны предложить механизм централизованной обработки ошибок авторизации (истечение токена, необходимость повторного вызова) без дублирования кода в каждом методе API. В рамках предложенной гексагональной архитектуры у нас есть транспортный адаптер (КоннекторHTTP) и аутентификатор, но они не знают о доменной логике повторных попыток. Это можно сделать, не нарушая чистоты доменных методов, если реализовать декоратор для транспортного адаптера или расширить аутентификатор.

Варианты:

    Создать обработку-обёртку над HTTP-клиентом ("HTTP-клиент с обновлением токена"), которая внутри выполняет запрос, при 401 вызывает метод обновления токена у аутентификатора (который должен предоставлять функцию ОбновитьТокен()), и повторяет запрос. Доменные методы используют этот улучшенный клиент, не зная о деталях.

    Использовать паттерн "цепочка обязанностей" или middleware в транспортном слое. Поскольку в 1С нет встроенных middleware, можно в общем модуле HTTP-клиента реализовать параметр "ПовторятьПри401", но это всё равно требует логики обновления токена, которая зависит от сервиса. Лучше внедрить эту логику на уровне фасада (обработки GitLab), но централизованно.

Предложу подход: в обработке-клиенте (доменном сервисе) создать приватный метод ВыполнитьЗапросСАвторизацией(Метод, Путь, Тело, ДопЗаголовки), который внутри обрабатывает 401, обновляет токен через метод ОбновитьТокен(), и повторяет запрос. Все публичные методы API используют этот приватный метод вместо прямого вызова HTTP-клиента. Это централизует логику в одном месте. При этом доменные методы остаются чистыми (они не видят этой логики). Чтобы не зависеть от конкретного сервиса, можно вынести логику обновления токена в адаптер аутентификации, у которого есть методы ДобавитьАвторизацию(Заголовки) и ОбработатьОшибкуАвторизации(). Тогда приватный метод будет универсальным для любого сервиса.

Важно: при обновлении токена нужно избежать бесконечного цикла (если новый токен тоже не работает). Введем максимум одну попытку обновления.

Также нужно обеспечить потокобезопасность, если обработка используется в фоновых заданиях. Лучше хранить токен внутри обработки, а при обновлении синхронизировать через блокировку (но для 1С это редкость, можно обойтись без неё, если обработка — отдельный экземпляр на сеанс).

    Единая точка обработки – логика обновления токена и повтора находится в одном месте.

    Чистые бизнес-методы – они не содержат технических деталей авторизации.

    Гибкость – для сервисов без refresh-токенов (как GitLab) метод просто не делает дополнительной работы.

    Тестируемость – можно в yaxUnit перегрузить ВыполнитьЗапросСАвторизацией, чтобы проверить сценарии с 401, не трогая реальный токен.

Этот подход элегантно решает задачу централизованной обработки ошибок авторизации, не загромождая публичное API.
